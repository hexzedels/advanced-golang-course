## Порядок, а не время

Давайте начнем с демо 1. На одном CPU восемь горутин по очереди увеличивают общий счетчик `n`
без синхронизации. Ответ правильный, 800 000. А `-race` сообщает о гонке:

```
$ GOMAXPROCS=1 go run -race ./01-counter
want 800000
WARNING: DATA RACE
Read at 0x00c000018158 by goroutine 8:
  main.broken.func1()
      course/w03/demos/01-counter/main.go:21 +0x37

Previous write at 0x00c000018158 by goroutine 15:
  main.broken.func1()
      course/w03/demos/01-counter/main.go:21 +0x49

Goroutine 8 (running) created at:
...
Goroutine 15 (finished) created at:
...
unsynchronized   got   800000  lost      0
```

Что мы здесь видим? Гонка между двумя горутинами из восьми: 15 писала в `n`, 8 потом читает. Горутина
15 к этому моменту уже завершилась (`finished`). На одном CPU они и правда не пересекались по
времени.

**Сказано (12:19):** «Эту гонку мы получаем не потому, что… Горутина, которая писала, к тому
моменту завершилась, по времени они не пересекались. Но -race все равно сообщает эту гонку из-за
того, что видит эту связь happens-before.»

Про время на лекции было верно. Неверна причина: `-race` сообщает о гонке, потому что связи
happens-before между этими доступами **нет**. Горутины 8 и 15 обе запустил main. От main к каждой
из них связь у нас есть. А от 15 к 8 нет ничего: ни канала, ни мьютекса, ни атомика. То, что
планировщик запустил их по очереди, связью не считается. Это плашка L3-02.

Получается, гонку определяет не время, а порядок, который задает сама программа. Давайте
разберемся, что это за порядок.

## Три отношения

Модель памяти Go строит happens-before из двух отношений
([go_mem.html#L119-L154](https://github.com/golang/go/blob/go1.27.1/doc/go_mem.html#L119-L154)).

1. **Sequenced before.** Порядок внутри одной горутины, как он записан в коде. `payload = 1` и
   следующая за ним строка той же горутины связаны так всегда.
2. **Synchronized before.** Связь между горутинами. Она возникает, когда синхронизирующее
   чтение видит синхронизирующую запись. Синхронизирующие операции это атомики, мьютекс и
   каналы: прием и `Lock` работают как чтение, отправка, `close` и `Unlock` как запись
   ([go_mem.html#L109-L111](https://github.com/golang/go/blob/go1.27.1/doc/go_mem.html#L109-L111)).
3. **Happens before.** Все цепочки, которые можно собрать из первых двух: шаг внутри горутины,
   переход в другую горутину по связи, снова шаг внутри.

Теперь гонка. Это два доступа к одной ячейке, и хотя бы один из них запись. Хотя бы один не
атомарный. И happens-before не упорядочивает их ни в одну сторону
([go_mem.html#L170-L183](https://github.com/golang/go/blob/go1.27.1/doc/go_mem.html#L170-L183)).
Отсюда плашка L3-04: атомарное и обычное чтение одной ячейки не гонка, нужна запись.

Что дает программа без гонок? Ее результат объясняется одним общим порядком всех операций, где
у каждой горутины ее порядок сохранен
([go_mem.html#L193-L198](https://github.com/golang/go/blob/go1.27.1/doc/go_mem.html#L193-L198)).
Это DRF-SC. Горутины при этом работают параллельно, то есть «последовательно» здесь не значит
«по очереди» (плашка L3-03). И обещание в одну сторону: если гонка есть, модель не обещает
ничего. Ответ при этом может выйти правильным, как в демо 1 выше (плашка L3-01).

И одно правило про атомики, которое на лекции прозвучало наоборот (плашка L3-05). Если атомарная
операция B увидела результат атомарной операции A, то A synchronized before B
([go_mem.html#L601-L604](https://github.com/golang/go/blob/go1.27.1/doc/go_mem.html#L601-L604)).
Связь следует из наблюдения. Запомним его: ниже окажется, что на нем стоят все остальные правила.

## Одиннадцать случаев демо 4

Каждый случай демо 4 устроен одинаково. Горутина пишет `payload = 1` и делает синхронизирующую
операцию. Main делает парную операцию и читает `payload`. Вопрос один: есть ли цепочка

## Случай 05 построчно

Вот код случая 05
([`demos/04-edges/main.go:66–73`](../../demos/04-edges/main.go#L66-L73)):

```go
func chanRecvSendBuffered(done chan struct{}) {
	reset()
	c := make(chan int, 1)
	go func() { payload = 1; <-c }()
	c <- 0
	sink = payload
	close(done)
}
```

Давайте пройдем по строкам. Что у нас в строке 69? Горутина пишет `payload = 1` и потом принимает
из канала.
В строке 70 main отправляет. В строке 71 main читает `payload`. Чем это отличается от случая 04?
Только емкостью канала, `1` вместо `0`.

В случае 04 буфера нет. Отправка не может завершиться, пока ее не примет получатель. Поэтому
правило говорит: прием synchronized before завершения отправки. Цепочка получается такая:
`payload = 1` → `<-c` в горутине → завершение `c <- 0` в main → чтение `payload`. Получается, связь есть.

В случае 05 у нас в канале есть свободный слот, и отправка в получателе не нуждается. Рантайм кладет
значение в буфер и сразу возвращается
([`chan.go:235–249`](https://github.com/golang/go/blob/go1.27.1/src/runtime/chan.go#L235-L249)):

```go
		typedmemmove(c.elemtype, qp, ep)
		c.sendx++
		if c.sendx == c.dataqsiz {
			c.sendx = 0
		}
		c.qcount++
		unlock(&c.lock)
		return true
	}
```

То есть отправка завершилась, а горутина, может быть, еще даже не запускалась. Правило для
буфера это учитывает: k-й прием synchronized before завершения (k+C)-й отправки. При C = 1 первый
прием связан со второй отправкой. А второй отправки в случае 05 нет. Связь от горутины к main
есть только одна, `go`, и она идет в обратную сторону. Модель памяти разбирает ровно этот пример
и прямо пишет, что с буфером «hello, world» не гарантирован
([go_mem.html#L449-L452](https://github.com/golang/go/blob/go1.27.1/doc/go_mem.html#L449-L452)).

Это и ответ на вопрос из зала. С буфером отправка не ждет получателя, и в этом все отличие.

![Три варианта: без буфера связь есть, с буфером на 1 связи нет, со второй отправкой связь возвращается](assets/l3-07-edges.svg)

На лекции отчет `-race` для случая 05 показал как раз это: main прочитал `payload` (строка 71)
раньше, чем горутина записала (строка 69).

## Проверим: что читает main

Модель говорит, что гарантии нет. А что происходит на самом деле? Давайте посмотрим.

Программа [`l3-07-probe`](l3-07-probe/main.go) повторяет случаи 04 и 05 по 100 000 раз в одном
процессе. Она считает, сколько раз main прочитал 0, то есть старое значение. И добавляет два
варианта случая 05:

- **05b**: та же программа, но main отправляет дважды. Вторая отправка не завершится, пока
  горутина не примет первое значение. Это правило k + C с k = 1.
- **05s**: та же программа, но main спит 1 мс между отправкой и чтением. Это проверка времени:
  меняется только то, когда main читает. Этот вариант идет не больше 2000 повторов.

Что мы видим? В случае 05 main читает 0 почти всегда: в 99 996–100 000 повторах из 100 000. Буфер
принимает значение сразу, и main успевает прочитать раньше, чем горутина вообще запускается. Со
второй отправкой (05b) связь возвращается: 0 нулей, и `-race` молчит.

А 05s самое интересное. Main читает на миллисекунду позже и получает правильное значение, 1, в
2000 повторах из 2000. А `-race` все равно сообщает о гонке, в 20 запусках из 20. Время поменяло
ответ, но не гонку. Получается, то же, что в демо 1: гонка это отсутствие связи, а не неудачное
время.

## Три правила без демо: init, TryLock, SetFinalizer

**init.** Правило: если пакет p импортирует q, init пакета q завершается до старта init пакета p.
А все init завершаются до старта `main.main`
([go_mem.html#L294-L302](https://github.com/golang/go/blob/go1.27.1/doc/go_mem.html#L294-L302)).
За счет чего? Все init вызывает рантайм в `runtime.main`. Он вызывает их по очереди, в том
порядке, который посчитал линкер
([`proc.go:268–273`](https://github.com/golang/go/blob/go1.27.1/src/runtime/proc.go#L268-L273)):

```go
	last := lastmoduledatap // grab before loop starts. Any added modules after this point will do their own doInit calls.
	for m := &firstmoduledata; true; m = m.next {
		doInit(m.inittasks)
		if m == last {
			break
		}
	}
```

Потом в той же горутине вызывается `main.main`
([`proc.go:301–302`](https://github.com/golang/go/blob/go1.27.1/src/runtime/proc.go#L301-L302)).
То есть init и main это одна горутина, и порядок между ними обычный, sequenced before. Поэтому
драйвер, который зарегистрировался в init, main видит без всякой синхронизации.

**TryLock.** Удачный `TryLock` равен `Lock`. Неудачный не синхронизирует ничего. И модель
разрешает `TryLock` вернуть false, даже когда мьютекс свободен
([go_mem.html#L537-L544](https://github.com/golang/go/blob/go1.27.1/doc/go_mem.html#L537-L544)).
Почему? Давайте посмотрим на код
([`internal/sync/mutex.go:76–80`](https://github.com/golang/go/blob/go1.27.1/src/internal/sync/mutex.go#L76-L80)):

```go
func (m *Mutex) TryLock() bool {
	old := m.state
	if old&(mutexLocked|mutexStarving) != 0 {
		return false
	}
```

Что мы видим? Первое чтение `m.state` обычное, не атомарное. Если оно увидело «занят», `TryLock` возвращает false,
не сделав ни одной атомарной операции. Значит, синхронизироваться тут не с чем. Если «свободен»,
дальше идет CAS. Он тоже может не пройти, если в этот момент изменилось состояние мьютекса
([`mutex.go:85–87`](https://github.com/golang/go/blob/go1.27.1/src/internal/sync/mutex.go#L85-L87)).
Что из этого следует на практике? По false от `TryLock` нельзя делать вывод о том, что сделал
другой владелец мьютекса.

**SetFinalizer.** Правило: вызов `SetFinalizer(x, f)` synchronized before вызова `f(x)`
([go_mem.html#L615-L618](https://github.com/golang/go/blob/go1.27.1/doc/go_mem.html#L615-L618)).
То есть все, что горутина записала до `SetFinalizer`, финализатор увидит. А вот когда он
сработает, не обещано. Финализатор запускается когда-нибудь после того, как GC нашел объект
недостижимым. И нет гарантии, что это случится до выхода из программы
([`mfinal.go:371–373`](https://github.com/golang/go/blob/go1.27.1/src/runtime/mfinal.go#L371-L373)).
Все финализаторы выполняет одна отдельная горутина, по очереди
([`mfinal.go:417`](https://github.com/golang/go/blob/go1.27.1/src/runtime/mfinal.go#L417)).
Поэтому «работает при завершении программы» неверно, это плашка L3-06. Для нового кода
документация советует `runtime.AddCleanup`
([`mfinal.go:351–352`](https://github.com/golang/go/blob/go1.27.1/src/runtime/mfinal.go#L351-L352)).

## За счет чего: все сводится к атомикам

Теперь главный вопрос из зала: это просто так написано? Правила действительно записаны в документе,
это договор. А выполняет его рантайм, и всегда одним способом. Каждый примитив устроен так, что
горутина, что ждет, атомарно читает то, что атомарно записала та, что отпускает. Дальше работает правило
атомиков: увидел, значит synchronized before. Давайте пройдем по примитивам.

**Мьютекс.** `Unlock` сбрасывает бит атомарным сложением
([`internal/sync/mutex.go:194`](https://github.com/golang/go/blob/go1.27.1/src/internal/sync/mutex.go#L194)),
а `Lock` берет мьютекс CAS-ом из 0
([`mutex.go:63`](https://github.com/golang/go/blob/go1.27.1/src/internal/sync/mutex.go#L63)):

```go
	if atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked) {
```

Получается, CAS пройдет, только если увидит 0, то есть результат `Unlock`. Это и есть случай 07.

**Каналы.** Любая операция с каналом идет под `c.lock`
([`chan.go:222`](https://github.com/golang/go/blob/go1.27.1/src/runtime/chan.go#L222)). Лок
рантайма на amd64 на быстром пути это одна инструкция `XCHG` и при захвате, и при отпускании
([`lock_spinbit.go:174`](https://github.com/golang/go/blob/go1.27.1/src/runtime/lock_spinbit.go#L174),
[`:284`](https://github.com/golang/go/blob/go1.27.1/src/runtime/lock_spinbit.go#L284)):

```go
	v8 := atomic.Xchg8(k8, mutexLocked)
```

Кто взял `c.lock` после другого, тот увидел его отпускание. Значит, все, что тот успел сделать
под локом и до него, упорядочено. Как мы помним из второй лекции, горутина, что ждет, при этом лежит в
очереди канала. В случае 04 возможны два порядка. Если горутина пришла к `<-c` первой, она ждет в
`recvq`, и main находит ее под тем же локом
([`chan.go:228–233`](https://github.com/golang/go/blob/go1.27.1/src/runtime/chan.go#L228-L233)).
Если первым пришел main, он ждет в `sendq`. Тогда горутина под локом забирает значение и будит
main через `goready`. А `goready` кладет main в `runnext` CAS-ом
([`proc.go:493–497`](https://github.com/golang/go/blob/go1.27.1/src/runtime/proc.go#L493-L497)), как в пункте про `go` ниже. В обоих
порядках между `<-c` и завершением `c <- 0` стоит цепочка атомарных операций.

**`go`.** Новая горутина попадает в `runnext` текущего P через CAS
([`proc.go:5341`](https://github.com/golang/go/blob/go1.27.1/src/runtime/proc.go#L5341),
[`:7548`](https://github.com/golang/go/blob/go1.27.1/src/runtime/proc.go#L7548)). Тот, кто ее
запустит, снимает ее оттуда тоже CAS-ом
([`:7655`](https://github.com/golang/go/blob/go1.27.1/src/runtime/proc.go#L7655)). Все, что main
записал до `go`, горутина увидит. Это случай 01.

**WaitGroup.** Счетчик лежит в одном атомарном слове `state`. `Done` атомарно вычитает единицу
([`waitgroup.go:104`](https://github.com/golang/go/blob/go1.27.1/src/sync/waitgroup.go#L104)),
`Wait` атомарно читает слово и возвращается, если счетчик 0
([`waitgroup.go:165–170`](https://github.com/golang/go/blob/go1.27.1/src/sync/waitgroup.go#L165-L170)).
Если счетчик не 0, `Wait` засыпает на семафоре, и последний `Done` его будит
([`:142`](https://github.com/golang/go/blob/go1.27.1/src/sync/waitgroup.go#L142)). Документация
пишет это прямо: `Done` synchronizes before возврата `Wait`
([`:151–152`](https://github.com/golang/go/blob/go1.27.1/src/sync/waitgroup.go#L151-L152)).

**Once.** Быстрый путь это атомарное чтение флага `done`
([`once.go:67`](https://github.com/golang/go/blob/go1.27.1/src/sync/once.go#L67)). Медленный
путь идет под мьютексом, и флаг ставится только после того, как `f` вернулась
([`once.go:74–77`](https://github.com/golang/go/blob/go1.27.1/src/sync/once.go#L74-L77)):

```go
	o.m.Lock()
	defer o.m.Unlock()
	if !o.done.Load() {
		defer o.done.Store(true)
```

Кто увидел `done == true`, тот увидел и все, что сделала `f`.

**Процессор.** А что делает сам атомик? На amd64 компилятор превращает операции `sync/atomic` в
такие инструкции
([`AMD64.rules`](https://github.com/golang/go/blob/go1.27.1/src/cmd/compile/internal/ssa/_gen/AMD64.rules#L500-L525)):

| операция | инструкция | строка |
|---|---|---|
| `Load` | обычный `MOV` | [500](https://github.com/golang/go/blob/go1.27.1/src/cmd/compile/internal/ssa/_gen/AMD64.rules#L500) |
| `Store` | `XCHG` | [507](https://github.com/golang/go/blob/go1.27.1/src/cmd/compile/internal/ssa/_gen/AMD64.rules#L507) |
| `Add` | `LOCK XADD` | [517](https://github.com/golang/go/blob/go1.27.1/src/cmd/compile/internal/ssa/_gen/AMD64.rules#L517) |
| `CompareAndSwap` | `LOCK CMPXCHG` | [525](https://github.com/golang/go/blob/go1.27.1/src/cmd/compile/internal/ssa/_gen/AMD64.rules#L525) |

Получается, запись, сложение и CAS это locked-инструкции. Intel пишет про них две вещи. Чтения и
записи не переставляются с locked-инструкциями. А буфер записей при locked-операции всегда
сливается в память. То есть такая инструкция работает как барьер (Intel SDM, том 3A, 253668-093,
§11.2.2 и §14.10). Почему тогда чтение остается обычным `MOV`? На x86 чтения не переставляются с
другими чтениями, а записи с более ранними чтениями (там же, §11.2.2). Демо 3 показало это на
лекции: с обычными записями оба нуля бывали, с `atomic.Int32` ни разу.

**А `-race`?** Он не смотрит на время и не смотрит на инструкции. Рантайм сам сообщает ему о
каждой связи. `Lock` вызывает `race.Acquire`
([`mutex.go:64–66`](https://github.com/golang/go/blob/go1.27.1/src/internal/sync/mutex.go#L64-L66)),
каналы отмечают каждый слот буфера
([`chan.go:926–955`](https://github.com/golang/go/blob/go1.27.1/src/runtime/chan.go#L926-L955)).
Поэтому `-race` и находит гонку там, где по времени все прошло правильно, как в демо 1 и 05s.

Что у нас получается в итоге? Правила записаны в модели памяти. Рантайм выполняет их через
атомарные операции, а процессор гарантирует, что атомарные операции видят друг друга в одном
порядке. `-race` проверяет те же правила по подсказкам рантайма.

  «барьер» наше: Intel пишет, что чтения и записи с ними не переставляются.

## Проверить самому

Из папки `demos` недели 3:

```sh
go run -race ./04-edges 05
for n in 01 02 03 04 05 06 07 08 09 10 11; do go run -race ./04-edges $n; done
GOMAXPROCS=1 go run -race ./01-counter
```

В случаях 02, 05 и 10 будет `WARNING: DATA RACE` и `exit status 66`, в остальных отчета нет. В
демо 1 смотрите на `Goroutine … (finished)`: писала горутина, которая уже завершилась.


ни одного, у 05s ни одного. Вторая пройдет без отчета, третья выдаст гонку. На 8 и на 4 CPU
